# طراحی فاز ۲A: استودیوی محتوا و Voice اصلی

تاریخ: ۲۰۲۶-۰۸-۲۹

وضعیت: مصوب در گفتگو، آماده بازبینی سند

مرجع بالادستی: `docs/superpowers/specs/2026-08-28-agentic-content-platform-design.md`

## ۱. هدف

این فاز جریان واقعی «انتخاب محصول ← ورود خلاصه مدیر ← ساخت پیش‌نویس ساختاریافته ← ویرایش ← تأیید» را به پنل اضافه می‌کند و امکان ضبط یا بارگذاری Voice اصلی مدیر را فراهم می‌سازد. نبود OpenAI API Key نباید مانع ساخت و آزمودن دیتابیس، رابط کاربری، نسخه‌بندی، کنترل صحت ورودی و Voice شود.

در پایان این فاز، خروجی Provider آزمایشی هرگز به‌عنوان کیفیت نهایی هوش مصنوعی معرفی نمی‌شود. اتصال واقعی OpenAI برای متن و تصویر Gate جداگانه‌ای است که پس از دریافت API Key و Billing انجام خواهد شد.

## ۲. محدوده دقیق

### داخل این فاز

- پروفایل برند قابل‌ویرایش با نام، شعار، مخاطب، لحن، آیدی پشتیبانی، CTA پیش‌فرض و ادعاهای تأییدشده؛
- ایجاد پیش‌نویس محتوا برای یک محصول فعال؛
- ورود خلاصه، هدف و زاویه محتوا توسط مدیر؛
- تولید خروجی ساختاریافته شامل تیتر، بدنه، مزایا، CTA، ایموجی و هشتگ؛
- Provider مستقل از OpenAI و یک Provider آزمایشی قطعی برای تست جریان؛
- ذخیره هر تولید یا بازتولید به‌عنوان نسخه مستقل؛
- ویرایش Caption نهایی بدون تغییر اطلاعات اصلی محصول؛
- وضعیت‌های `draft`، `waiting_approval`، `approved`، `rejected` و `superseded`؛
- ضبط Voice در مرورگر یا بارگذاری فایل صوتی؛
- حفظ بایت‌های Voice اصلی بدون Trim، حذف نویز، تغییر سرعت، تبدیل صدا یا بازنویسی؛
- پخش، حذف و جایگزینی Voice پیش از تأیید؛
- پیش‌نمایش یکپارچه محصول، Caption و Voice؛
- تست واحد، Integration و تست دستی این جریان.

### خارج از این فاز

- تماس واقعی OpenAI و ارزیابی کیفیت زبانی مدل؛
- ویرایش مولد عکس، حذف پس‌زمینه و رندر لوگو/متن روی عکس؛
- زمان‌بندی و انتشار در Telegram، Bale، Rubika یا WhatsApp؛
- تبدیل فنی Voice برای پلتفرم‌ها؛
- Auto Mode، Scheduler، پاسخ‌گویی مشتری و Analytics.

## ۳. تصمیم‌های معماری

### ۳.۱ مرز Provider

ماژول `content` فقط قرارداد زیر را می‌شناسد:

- `ContentGenerationRequest`: اطلاعات واقعی محصول، اطلاعات برند و Brief مدیر؛
- `GeneratedContent`: `headline`، `body`، `benefits`، `cta`، `hashtags`، `used_emojis` و `content_angle`؛
- `ContentProvider.generate(request) -> GeneratedContent`.

پیاده‌سازی اولیه `TemplateContentProvider` است. این Provider با قالب‌های قطعی فارسی، خروجی کامل‌تر از Brief می‌سازد، ایموجی و هشتگ اضافه می‌کند و برای تست قابل تکرار است. نام Provider و عبارت «حالت آزمایشی — بدون OpenAI» در پیش‌نمایش نمایش داده می‌شود. هیچ مسیری اجازه ندارد آن را Provider تولیدی تلقی کند.

Provider واقعی OpenAI بعداً همین قرارداد را پیاده‌سازی می‌کند؛ Route، Service، دیتابیس و Templateهای پنل نباید برای تعویض Provider تغییر کنند.

### ۳.۲ منبع حقیقت و جلوگیری از ادعای ساختگی

حقایق مجاز فقط از این منابع می‌آیند:

1. فیلدهای محصول شامل نام، قیمت، موجودی، ارسال، ویژگی‌ها و Tagها؛
2. ادعاهای تأییدشده پروفایل برند؛
3. Brief همان پیش‌نویس که مدیر صریحاً وارد می‌کند.

توضیحات محصول با تولید محتوا بازنویسی نمی‌شود. Provider آزمایشی فقط همین مقادیر را بازآرایی می‌کند. قیمت، گارانتی، ضخامت، زمان تحویل و ارسال در صورت نبود داده حذف می‌شوند. Caption نهایی قابل ویرایش است، اما نسخه خروجی Provider جداگانه و تغییرناپذیر نگهداری می‌شود تا سابقه قابل بررسی باشد.

### ۳.۳ هویت محتوایی هایکا

پروفایل اولیه با داده‌های عمومی کانال هایکا ساخته می‌شود، اما مدیر می‌تواند آن را پیش از استفاده اصلاح کند. پیش‌فرض لحن:

- تخصصی، حرفه‌ای، مطمئن و روان؛
- خطاب یکدست و محترمانه؛
- مناسب کابینت‌سازان و خریداران جدی؛
- ایموجی محدود و مرتبط؛
- فاصله‌گذاری و علائم نگارشی استاندارد فارسی؛
- CTA روشن و یک‌بار در انتهای متن؛
- سه تا شش هشتگ مرتبط، بدون تکرار.

ساختار Caption پیش‌فرض: Hook کوتاه، معرفی، سه تا پنج نکته یا مزیت، اعتمادساز تأییدشده، CTA، آیدی پشتیبانی و هشتگ‌ها. مدیر می‌تواند زاویه‌های `product_intro`، `educational`، `faq`، `problem_solution`، `trust` و `order_guide` را انتخاب کند.

## ۴. مدل داده

### `BrandProfile`

- `id`
- `business_name`
- `tagline`
- `audience`
- `tone_guidelines`
- `support_handle`
- `default_cta`
- `approved_claims` به‌صورت فهرست JSON
- `default_hashtags` به‌صورت فهرست JSON
- `created_at` و `updated_at`

MVP فقط یک پروفایل برند فعال دارد. Secret یا Token در این جدول ذخیره نمی‌شود.

### `ContentDraft`

- `id`
- `product_id`
- `parent_id` برای نسخه قبلی، در صورت بازتولید
- `revision` از ۱ و افزایشی در زنجیره نسخه‌ها
- `user_brief`
- `requested_angle`
- `provider_name`
- `provider_payload` شامل خروجی ساختاریافته و معتبر
- `final_caption`
- `status`
- `created_at`، `updated_at` و `approved_at`

ویرایش Caption همان Draft را به‌روزرسانی می‌کند و خروجی خام Provider را تغییر نمی‌دهد. Regenerate یک ردیف جدید با `parent_id` و `revision` جدید می‌سازد. فقط یک نسخه در هر زنجیره می‌تواند `approved` باشد؛ هنگام تأیید نسخه جدید، نسخه تأییدشده قبلی به `superseded` تغییر می‌کند تا هم تاریخچه حفظ شود و هم تأیید فعال ابهام نداشته باشد.

### `MediaAsset`

- `id`
- `content_draft_id`
- `kind` با مقدار اولیه `voice_original`
- `relative_path` با نام opaque و خارج از مسیر عمومی Static؛
- `mime_type`
- `size_bytes`
- `sha256`
- `duration_ms` در صورت ثبت معتبر مرورگر؛
- `created_at`

در این فاز هر Draft حداکثر یک Voice فعال دارد. جایگزینی، رکورد قبلی را از Draft جدا می‌کند و فایل قبلی را پس از Commit موفق حذف می‌کند.

## ۵. جریان‌های پنل

### پروفایل برند

مسیر «تنظیمات برند» فرم تک‌صفحه‌ای دارد. ادعاهای تأییدشده و هشتگ‌های پیش‌فرض به‌شکل ردیف‌های قابل افزودن وارد می‌شوند. داده‌های نمونه کانال فقط مقدار اولیه‌اند و مدیر مسئول تأیید نهایی آن‌ها است.

### ساخت محتوا

1. مدیر از صفحه محصول «ساخت محتوا» را انتخاب می‌کند.
2. محصول و حقایق ثبت‌شده در کنار فرم نمایش داده می‌شوند.
3. مدیر Brief، هدف و زاویه را وارد می‌کند.
4. Service یک Snapshot ورودی می‌سازد و Provider را فراخوانی می‌کند.
5. Schema خروجی را اعتبارسنجی و Caption نهایی را مونتاژ می‌کند.
6. Draft با وضعیت `waiting_approval` ذخیره می‌شود.
7. صفحه پیش‌نمایش Provider آزمایشی را واضح نمایش می‌دهد.
8. مدیر متن را ویرایش، بازتولید، رد یا تأیید می‌کند.

Brief خالی، محصول غیرفعال، پروفایل برند ناقص یا خروجی نامعتبر Provider با پیام فارسی و بدون ایجاد Draft ناقص رد می‌شود.

### Voice

پنل از `MediaRecorder` استفاده می‌کند و MIME پشتیبانی‌شده مرورگر را با ترتیب WebM/Opus و سپس Ogg/Opus انتخاب می‌کند. مدیر می‌تواند قبل از Upload ضبط را پخش و حذف کند. بارگذاری دستی MP3، M4A، OGG، WAV و WebM نیز پذیرفته می‌شود.

محدودیت اولیه حجم ۲۵ MiB و زمان ضبط مرورگر ۱۰ دقیقه است. Extension، MIME، Signature و اندازه روی سرور بررسی می‌شوند. `duration_ms` مرورگر صرفاً برای نمایش و کنترل رابط است و مبنای امنیتی نیست. بررسی قطعی مدت و تولید نسخه‌های سازگار در فاز اتصال پلتفرم با FFprobe انجام می‌شود.

Voice از Route نیازمند Session مدیر با پشتیبانی HTTP Range پخش می‌شود و هرگز زیر mount عمومی `/uploads` قرار نمی‌گیرد. فایل اصلی تغییر نمی‌کند و Hash آن پس از ذخیره ثبت می‌شود.

## ۶. خطا و تراکنش

- شکست Provider هیچ Draft نیمه‌کاره‌ای ذخیره نمی‌کند.
- شکست ذخیره Voice، رکورد دیتابیس ایجاد نمی‌کند.
- شکست Commit پس از ذخیره فایل، فایل جدید را پاک می‌کند.
- حذف یا جایگزینی فقط پس از Commit موفق دیتابیس فایل قبلی را حذف می‌کند.
- خطاهای UI فارسی و قابل اقدام‌اند؛ جزئیات فنی در Log ساختاریافته ثبت می‌شوند.
- مسیر فایل از شناسه‌های دیتابیس و نام تصادفی ساخته می‌شود؛ نام فایل کاربر در مسیر استفاده نمی‌شود.
- CSRF برای Generate، Edit، Approve، Reject، Regenerate، Upload و Delete الزامی است.
- تمام صفحات و رسانه‌های این فاز نیازمند ورود مدیر هستند.

## ۷. آزمون و معیار پذیرش

### تست خودکار

- ساخت و ویرایش پروفایل برند و Normalize شدن Handle/Hashtag؛
- ساخت درخواست Provider فقط از حقایق مجاز؛
- خروجی قطعی Template Provider برای یک ورودی ثابت؛
- رد خروجی ناقص یا هشتگ تکراری؛
- ایجاد Draft و حفظ Snapshot خروجی Provider؛
- Regenerate و افزایش صحیح Revision؛
- فقط یک نسخه Approved در هر زنجیره؛
- عدم تغییر Product هنگام ویرایش Caption؛
- رد Voice با Extension، MIME، Signature یا حجم نامعتبر؛
- یکسان بودن SHA-256 فایل ورودی و Voice ذخیره‌شده؛
- پاک‌سازی فایل در خطای دیتابیس و جایگزینی امن؛
- محافظت Login و CSRF برای تمام Routeها؛
- پخش Voice فقط برای مدیر واردشده؛
- نمایش صریح Provider آزمایشی در UI؛
- اجرای کامل Migration upgrade/downgrade.

### تست دستی کاربر

1. پروفایل برند را بازبینی و ذخیره کند.
2. یک محصول واقعی را انتخاب و فقط یک Brief کوتاه وارد کند.
3. تیتر، مزایا، CTA، ایموجی و هشتگ‌های ساخته‌شده را ببیند.
4. Caption را ویرایش و ذخیره کند؛ Product نباید تغییر کند.
5. Regenerate کند و هر دو Revision را در تاریخچه ببیند.
6. با میکروفن مرورگر Voice ضبط، پخش، حذف و دوباره ضبط کند.
7. فایل صوتی دستی بارگذاری و همان فایل را بدون تغییر پخش کند.
8. Draft را تأیید و وضعیت آن را مشاهده کند.

Gate تکمیل این فاز: تمام تست‌های خودکار Pass، تست دستی بالا Pass و برچسب آزمایشی Provider در تمام پیش‌نمایش‌ها قابل مشاهده باشد. کیفیت نهایی متن و تصویر تا اتصال واقعی OpenAI پذیرفته یا رد نمی‌شود.

## ۸. مسیر اتصال OpenAI

پس از دریافت API Key:

1. Secret فقط در `.env` محلی یا Secret Store سرور قرار می‌گیرد؛
2. Provider واقعی متن با خروجی JSON ساختاریافته به قرارداد موجود اضافه می‌شود؛
3. Smoke Test کنترل‌شده روی یک محصول آزمایشی انجام می‌شود؛
4. Prompt براساس هویت هایکا و چند Caption تأییدشده تنظیم می‌شود؛
5. هزینه، زمان پاسخ، خروجی نامعتبر و خطاهای API ثبت می‌شوند؛
6. پس از تأیید کیفیت، Provider تولیدی از حالت آزمایشی جدا فعال می‌شود؛
7. فاز مستقل تصویر OpenAI آغاز می‌شود.

کلید API در گفتگو، Git، دیتابیس عادی، Screenshot یا Log قرار نمی‌گیرد.

# طراحی MVP سامانه هوشمند مدیریت محتوا و پاسخ‌گویی مشتری

تاریخ: ۲۰۲۶-۰۸-۲۸

وضعیت: آماده بازبینی کاربر

زبان و چارچوب اصلی: Python 3.12+ / FastAPI

## ۱. هدف و مرجع تصمیم‌گیری

هدف، ساخت یک MVP واقعی، تست‌شده و قابل‌استفاده برای تولید محتوای محصول، انتشار چندپلتفرمی و پاسخ‌گویی کنترل‌شده به مشتریان است. سامانه باید برای یک مدیر غیر‌فنی ساده باشد، ظاهر حرفه‌ای داشته باشد و بدون پیچیدگی‌های غیرضروری نگهداری شود.

ترتیب اعتبار نیازمندی‌ها چنین است:

1. تصمیم‌های مستقیم و جدید کارفرما/کاربر در گفتگو؛
2. سند PDF شرح خدمات؛
3. متن پیشنهادی هوش مصنوعی دیگر، فقط به‌عنوان نظر کمکی و نه دستور.

در تعارض‌ها، تصمیم جدید کاربر حاکم است. به‌ویژه، برخلاف پیشنهاد قدیمی «عدم تغییر پس‌زمینه»، ویرایش مولد عکس با OpenAI API و تعویض پس‌زمینه اکنون الزام قطعی است. Voice تبلیغاتی نیز به بسته محتوایی اضافه شده است.

## ۲. محدوده MVP

MVP شامل این جریان انتها‌به‌انتها است:

1. مدیر وارد پنل می‌شود.
2. محصول، قیمت و اطلاعات واقعی آن را ثبت می‌کند.
3. عکس خام محصول، لوگو و در صورت نیاز Voice را بارگذاری می‌کند.
4. موضوع، نکات اصلی، لحن و هدف محتوا را وارد می‌کند.
5. OpenAI API نسخه استودیویی عکس را می‌سازد؛ پس‌زمینه، نور و جلوه بصری اصلاح می‌شوند، اما هویت محصول باید حفظ شود.
6. سامانه لوگو و متن کوتاه دقیق را با رندر قطعی روی عکس قرار می‌دهد.
7. مدل متنی یک کپشن فارسی حرفه‌ای شامل تیتر، توضیح، مزایا، CTA، ایموجی و هشتگ تولید می‌کند.
8. مدیر عکس، متن و Voice را در یک پیش‌نمایش واحد می‌بیند.
9. در حالت دستی، مدیر ویرایش، بازتولید، تأیید یا رد می‌کند.
10. در حالت خودکار، Guardrailها قبل از زمان‌بندی و انتشار اجرا می‌شوند.
11. هر پلتفرم نتیجه مستقل دارد؛ شکست یکی موفقیت بقیه را برنمی‌گرداند.
12. مشتری از لینک ربات پین‌شده وارد گفت‌وگوی خصوصی می‌شود و سؤال مرتبط می‌پرسد.
13. پاسخ فقط بر اساس Product، FAQ و سیاست‌های ثبت‌شده تولید می‌شود.
14. داشبورد وضعیت انتشار، هزینه AI، سؤالات و خطاها را نمایش می‌دهد.

موارد خارج از MVP: پرداخت، ثبت سفارش، Checkout، CRM، اپلیکیشن موبایل، Vector Database، Microservices، Multi-Agent پیچیده، تحلیل تجاری پیشرفته، تولید ویدئو و تبدیل متن به صدای مصنوعی.

## ۳. اولویت اجرا و معیار کیفیت

کیفیت بر زمان تحویل مقدم است. کار به فازهای مستقل تقسیم می‌شود و ورود به فاز بعد فقط بعد از پاس‌شدن تست‌های همان فاز انجام می‌شود.

ترتیب اتصال واقعی پلتفرم‌ها:

1. Telegram
2. Bale
3. Rubika
4. WhatsApp در مرحله آخر و به‌صورت best-effort

نبود Token مانع ساخت Unit/Mock Test نمی‌شود، اما هیچ اتصال تست‌نشده‌ای «کامل» اعلام نخواهد شد.

## ۴. رویکرد معماری

### ۴.۱ انتخاب اصلی

سامانه یک **Modular Monolith** است. یک برنامه FastAPI، یک پایگاه داده و ماژول‌های داخلی با مرز روشن خواهیم داشت. این انتخاب برای MVP کم‌ریسک‌تر، سریع‌تر و قابل‌نگهداری‌تر از Microservices است.

پشته پیشنهادی:

- Python 3.12+
- FastAPI، Jinja2 و HTMX
- SQLAlchemy 2.x و SQLite؛ ساختار مدل‌ها قابل مهاجرت به PostgreSQL
- APScheduler برای زمان‌بندی
- httpx برای APIهای بیرونی
- Pydantic برای تنظیمات و خروجی ساختاریافته AI
- Pillow با پشتیبانی صحیح RTL/RAQM یا HarfBuzz برای ترکیب گرافیکی
- FFmpeg برای ساخت نسخه‌های فنی سازگار از Voice، بدون تغییر محتوای گفتار
- Chart.js برای نمودارهای سبک
- pytest برای تست

React/Next.js، Celery، Redis، Kafka، Kubernetes، LangChain و LangGraph وارد MVP نمی‌شوند مگر یک نیاز واقعی و اثبات‌شده ایجاد شود.

### ۴.۲ گزینه‌های ردشده

- ساخت محتوای جداگانه برای هر پیام‌رسان: کنترل بیشتری می‌دهد ولی دوباره‌کاری و ناسازگاری متن و رسانه ایجاد می‌کند.
- ارسال Payload کاملاً یکسان بدون Adapter: ساده به‌نظر می‌رسد ولی محدودیت فرمت، طول متن و Voice پلتفرم‌ها را نادیده می‌گیرد.

رویکرد منتخب، **Canonical Post Bundle + Platform Adapters** است: یک بسته مرکزی شامل تصویر، کپشن و Voice ساخته می‌شود و هر Adapter فقط آن را به فرمت سازگار پلتفرم خود تبدیل می‌کند.

## ۵. ماژول‌ها و مرزها

- `core`: تنظیمات، دیتابیس، امنیت، لاگ، زمان و خطاهای مشترک.
- `catalog`: محصول، ویژگی‌ها، قیمت، موجودی/دسترسی، ارسال و دارایی‌های برند.
- `campaigns`: کمپین، هدف، لحن، تقویم و جلوگیری ساده از تکرار محتوا.
- `content`: تولید کپشن، اعتبارسنجی، نسخه‌ها و سابقه بازتولید.
- `media`: آپلود امن، نسخه اصلی عکس، ویرایش OpenAI، ترکیب لوگو/متن و پردازش Voice.
- `publishing`: بسته پست، زمان‌بندی، حالت دستی/خودکار، Pause، Retry و نتیجه هر پلتفرم.
- `platforms`: Adapter مستقل Telegram، Bale، Rubika و WhatsApp.
- `support`: FAQ، بازیابی اطلاعات واقعی، مسیریابی سؤال، پاسخ و صف بررسی انسانی.
- `analytics`: KPI، نمودار، هزینه API و گزارش دوره‌ای.
- `admin`: صفحات Jinja2/HTMX و APIهای موردنیاز UI.

Business Logic نباید URL یا جزئیات API پیام‌رسان را بشناسد.

## ۶. مدل داده سطح بالا

حداقل موجودیت‌ها:

- `Product`: نام، توضیح، قیمت، وضعیت، موجودی اختیاری، ارسال، ویژگی‌ها، تگ‌ها.
- `BrandAsset`: لوگو، فونت، رنگ‌ها، اطلاعات تماس و قالب فعال.
- `Campaign`: هدف، بازه، روز/ساعت، تعداد پست، محصولات، لحن، یادداشت، Mode و Status.
- `Post`: ورودی کاربر، خروجی ساختاریافته AI، کپشن نهایی، وضعیت، زمان برنامه‌ریزی و نسخه.
- `MediaAsset`: نوع، مسیر امن، MIME، اندازه، Hash، نسخه Original/AI/Final/Voice.
- `Publication`: پلتفرم، مقصد، Attempt، Message IDها، نتیجه، خطا و زمان.
- `FAQ`: سؤال، جواب، دسته، محصول اختیاری و وضعیت.
- `Conversation`: پلتفرم، شناسه حداقلی کاربر، سؤال، پاسخ، منبع، وضعیت و زمان پاسخ.
- `AIUsage`: Provider، Model، Operation، Token/Request Usage، هزینه برآوردی و Request ID.
- `SystemSetting`: Pause سراسری و تنظیمات غیرمحرمانه قابل‌ویرایش.

Secretها فقط از Environment Variable یا Secret Store خوانده می‌شوند و در دیتابیس عادی یا Log ذخیره نمی‌شوند.

## ۷. خط تولید تصویر

### ۷.۱ ورودی و نگهداری

- فایل اصلی تغییرناپذیر نگهداری می‌شود.
- نوع، حجم و ابعاد فایل Validate می‌شوند.
- نام فایل تصادفی/امن است و Hash برای تشخیص تکرار ذخیره می‌شود.
- نسخه‌های `original`، `ai_edited` و `final_composite` جدا هستند.

### ۷.۲ ویرایش مولد

از OpenAI Image API و `gpt-image-2` در endpoint ویرایش استفاده می‌شود. Prompt باید صریحاً این قیود را اعمال کند:

- محصول، اجزا، فرم، نسبت‌ها، رنگ، متریال، لوگو/برچسب روی محصول و تعداد قطعات تغییر نکنند.
- هیچ قابلیت یا جزئیات جدیدی به محصول اضافه نشود.
- فقط محیط، پس‌زمینه، نور، سایه و Presentation تبلیغاتی اصلاح شوند.
- محصول کامل داخل قاب بماند و برای لوگو/تیتر فضای امن ایجاد شود.
- خروجی برای مقایسه با عکس اصلی قابل مشاهده باشد.

تنظیم پیش‌فرض MVP یک خروجی با کیفیت `high` است. تولید مجدد فقط با رد مدیر یا شکست کنترل کیفیت انجام می‌شود. Size و Quality در Settings قابل تغییرند تا هزینه کنترل شود.

### ۷.۳ کنترل کیفیت و ایمنی

در دوره دستی، مقایسه بصری Original/Generated الزامی است. در Auto Mode، حداقل این موارد کنترل می‌شوند:

- فایل خروجی وجود دارد و قابل Decode است.
- ابعاد و نسبت تصویر معتبرند و محصول Crop نشده است.
- محصول از نظر شکل و رنگ به ورودی وفادار است.
- OCR یا کنترل بصری نشان نمی‌دهد متن/لوگوی موجود روی خود محصول مخدوش شده است.
- Moderator یا API Error رخ نداده است.

هر شک در هویت محصول، وضعیت را `needs_review` می‌کند و انتشار خودکار ممنوع است.

برای Auto Mode، یک مدل Vision-capable عکس اصلی و خروجی را با Schema ثابت مقایسه می‌کند. نتیجه فقط `pass` یا `review` است و دلیل اختلاف ثبت می‌شود. خطای این بررسی، پاسخ نامعتبر یا نتیجه `review` همگی Fail-closed هستند. فعال‌کردن Auto برای هر Campaign تصمیم صریح مدیر است و سامانه صرفاً با گذشت چند روز آن را خودکار فعال نمی‌کند.

### ۷.۴ لوگو و متن روی تصویر

OpenAI مسئول تایپ نهایی فارسی نیست. لوگو، قیمت و متن کوتاه تبلیغاتی پس از تولید تصویر به‌شکل قطعی با Pillow و موتور RTL مناسب افزوده می‌شوند. قالب‌ها Safe Area، اندازه فونت، کنتراست، Shadow/Box و عدم هم‌پوشانی با محصول را رعایت می‌کنند.

کپشن کامل زیر عکس قرار می‌گیرد؛ تصویر فقط متن کوتاه، لوگو یا Badge مورد تأیید را حمل می‌کند. مدیر پیش از انتشار نسخه نهایی را می‌بیند.

## ۸. تولید متن و هشتگ

ورودی مدل شامل اطلاعات واقعی محصول، هدف، لحن، نکات مدیر، پلتفرم و خلاصه پست‌های قبلی کمپین است. خروجی JSON و Pydantic-validated شامل موارد زیر است:

- `headline`
- `body`
- `benefits`
- `cta`
- `hashtags`
- `used_emojis`
- `content_angle`

لحن پیش‌فرض محترمانه، حرفه‌ای، بیزینسی و روان است. ایموجی‌ها مرتبط و محدودند؛ هشتگ‌ها Normalized، بدون تکرار و متناسب با محصول هستند. قیمت، موجودی، شرایط ارسال و مشخصات فقط از دیتابیس وارد می‌شوند و مدل اجازه اختراع ندارد.

برای کاهش تکرار، Angle پست‌های قبلی کمپین ثبت می‌شود و از زاویه‌های ساده‌ای مثل معرفی، مزایا، کاربرد، FAQ، آموزش، اعتمادسازی، Problem/Solution و پیشنهاد ویژه استفاده می‌شود.

## ۹. Voice تبلیغاتی

Voice در MVP یک رسانه خروجی اختیاری برای پست است، نه صدای مصنوعی تولیدشده توسط AI.

جریان Voice:

1. مدیر فایل صوتی را Upload می‌کند یا از ورودی ضبط مرورگر استفاده می‌کند.
2. پنل امکان پخش و حذف/جایگزینی آن را می‌دهد.
3. MIME، حجم و مدت Validate می‌شوند.
4. نسخه اصلی حفظ و نسخه‌های سازگار با FFmpeg تولید می‌شوند؛ Trim، تغییر سرعت، حذف بخش یا بازنویسی گفتار انجام نمی‌شود.
5. همان Voice در تمام کانال‌های انتخاب‌شده منتشر می‌شود.

یک پست از نظر کسب‌وکار یک Bundle است، ولی ممکن است از نظر API دو پیام باشد: ابتدا عکس + Caption و بلافاصله Voice به‌صورت پیام دوم یا Reply به پیام اول.

- Telegram: ارسال Native Voice با `sendVoice`.
- Bale: ارسال Native Voice با `sendVoice`.
- Rubika: ابتدا Native/Audio در تست واقعی بررسی می‌شود؛ اگر API رسمی نوع Voice را ارائه نکند، همان صدا با `sendFile` به‌صورت فایل قابل‌پخش ارسال می‌شود.
- WhatsApp: در مرحله آخر و فقط در صورت موفقیت Connector آزمایشی.

Voice سؤال مشتری و پاسخ صوتی ربات در محدوده این MVP نیستند.

## ۱۰. انتشار، وضعیت‌ها و زمان‌بندی

حالت‌ها:

- `manual_approval`
- `automatic`
- `paused`

وضعیت پست:

- `draft`
- `generating`
- `waiting_approval`
- `approved`
- `scheduled`
- `publishing`
- `published`
- `partially_published`
- `failed`
- `needs_review`

در Manual Mode، هیچ انتشار بدون Approve انجام نمی‌شود. در Auto Mode، خالی‌نبودن کپشن، وجود تصویر، اعتبار JSON، عدم شباهت غیرعادی، مقصد معتبر، طول مناسب، ایمنی تصویر و Pause نبودن سامانه کنترل می‌شوند.

APScheduler با Timezone تنظیم‌شده کار می‌کند. هر عملیات Publication دارای Idempotency Key است تا Restart یا Retry باعث ارسال تکراری نشود. Retry فقط برای خطاهای موقت و حداکثر سه Attempt با Backoff محدود انجام می‌شود.

Pause All Publishing فوراً جلوی شروع Job جدید را می‌گیرد، اما عملیات شبکه‌ای که پیش‌تر شروع شده قابل Rollback تضمین‌شده نیست؛ نتیجه آن ثبت و در UI نشان داده می‌شود.

## ۱۱. قرارداد Adapterها

هر Adapter حداقل این قابلیت‌ها را اعلام می‌کند:

- `health_check()`
- `send_text()`
- `send_image_with_caption()`
- `send_voice_or_audio()`
- `send_post_bundle()`
- `receive_private_message()` در صورت پشتیبانی
- `capabilities()`

خروجی استاندارد شامل Success، External Message IDs، Retryability، Error Code و Safe Error Message است. Adapter نباید Secret را در خطا یا Log افشا کند.

مقصد Publishing در MVP فقط Channel است؛ ارسال تبلیغات به Group یا پیام مستقیم انبوه خارج از محدوده است. ربات برای Support فقط گفت‌وگوی خصوصی یک‌به‌یک را دریافت و پاسخ می‌دهد.

## ۱۲. دستیار پاسخ‌گویی مشتری

مشتری از لینک پین‌شده کانال وارد گفت‌وگوی خصوصی ربات همان پلتفرم می‌شود. مسیریابی پاسخ سه سطح دارد:

1. سؤال دقیق یا نزدیک به Product/FAQ: پاسخ قطعی از دیتابیس.
2. سؤال مرتبط با حوزه کسب‌وکار: LLM با Context محدودشده به داده‌های واقعی پاسخ را تدوین می‌کند.
3. سؤال بی‌ربط: رد مؤدبانه و حرفه‌ای بدون پاسخ محتوایی.

اگر داده کافی نباشد، ربات اعلام می‌کند پاسخ دقیق نیازمند بررسی است و Conversation را برای ادمین `needs_human_review` می‌کند. هیچ قیمت، موجودی، ضمانت یا سیاستی نباید توسط مدل ساخته شود.

## ۱۳. پنل ادمین

پنل با وجود ساده‌بودن باید شکیل، Responsive و منسجم باشد. صفحات اصلی:

- Dashboard
- Products
- Brand Assets
- Campaigns
- Create Post / Content Queue
- Post Preview با مقایسه Original/Generated/Final و پخش Voice
- Publications
- Conversations / Human Review
- FAQ
- Analytics
- Settings

Dashboard حداقل Campaign فعال، پست بعدی، Mode، Pause، موارد منتظر تأیید، شکست انتشار، سؤالات نیازمند بررسی، فعالیت اخیر و هزینه تقریبی AI را نشان می‌دهد.

## ۱۴. تحلیل و گزارش

KPIهای MVP:

- تعداد سؤالات روزانه و زمان متوسط پاسخ
- نرخ پاسخ قطعی و نرخ نیاز به بررسی انسانی
- موضوعات و محصولات پرتکرار
- تعداد پست‌های تولیدشده، تأییدشده و بازتولیدشده
- Manual در برابر Auto
- موفق/ناموفق انتشار به تفکیک پلتفرم
- خطاهای اخیر و Retryها
- هزینه برآوردی OpenAI به تفکیک تصویر، متن و دوره زمانی

نمودارها فقط برای تصمیم عملی طراحی می‌شوند: روند سؤالات، دسته‌بندی سؤال، محصولات پرتکرار، وضعیت انتشار و روند هزینه AI. گزارش سه‌روزه داخل پنل ساخته می‌شود؛ ارسال آن به Telegram Admin Bot فقط پس از کامل‌شدن MVP اصلی اضافه می‌شود.

## ۱۵. خطا، امنیت و حریم خصوصی

- همه تماس‌های خارجی Timeout، Exception Mapping و Structured Logging دارند.
- Secretها Redact می‌شوند.
- Upload فقط پس از بررسی Extension، MIME، Signature، Size و نام امن پذیرفته می‌شود.
- پنل حداقل Login امن، Password Hash، Session Cookie امن و CSRF Protection برای عملیات تغییردهنده دارد.
- داده مکالمه حداقلی است و داده حساس غیرضروری ذخیره نمی‌شود.
- `.env` Commit نمی‌شود و `.env.example` بدون مقدار محرمانه ارائه می‌شود.
- Session غیررسمی WhatsApp جدا، رمزگذاری‌شده و قابل حذف است.

## ۱۶. WhatsApp

WhatsApp پس از تکمیل و تست Telegram، Bale و Rubika بررسی می‌شود. چون کارفرما API رسمی پولی نمی‌خواهد و ارسال به کانال/گروه مدنظر است، Connector غیررسمی ممکن است ناپایدار یا منجر به محدودیت حساب شود.

قواعد:

- هیچ دورزدن CAPTCHA، Rate Limit یا مکانیزم امنیتی انجام نمی‌شود.
- Login فقط با QR/Pairing و حضور مالک حساب است.
- خرابی WhatsApp هسته را متوقف نمی‌کند.
- هر قابلیتی که واقعاً کار کند حفظ می‌شود؛ قابلیت ناموفق Skip و شفاف گزارش می‌شود.
- Adapter طوری باقی می‌ماند که بعداً با Cloud API رسمی قابل تعویض باشد.

## ۱۷. تست و شواهد تکمیل

تست‌ها به‌صورت مرحله‌ای نوشته و اجرا می‌شوند. هیچ تست خودکاری پیام واقعی به کاربر یا کانال تولید نمی‌کند مگر Smoke Test دستی با اکانت آزمایشی و تأیید مالک.

حداقل پوشش:

- Product/FAQ/Campaign CRUD و Validation
- Upload عکس/لوگو/Voice و رد فایل نامعتبر
- OpenAI image edit و text generation با Mock
- رندر صحیح فارسی، Logo Safe Area و حفظ ابعاد
- Manual Approval، Auto Guardrails و Pause
- Scheduler و Idempotency
- موفقیت جزئی چندپلتفرمی و Retry
- Telegram، Bale، Rubika و WhatsApp Adapter Mock
- Integration Test واقعی هر پلتفرم پس از دریافت Token
- Grounded Support، سؤال ناشناخته و سؤال بی‌ربط
- Analytics Aggregation و AI Cost Tracking
- Authentication و مسیرهای حساس پنل

هر فاز با اجرای تست مربوطه و ثبت نتیجه تمام می‌شود. ادعای «کامل» فقط با خروجی تست و، برای Integrationها، مشخص‌کردن واقعی یا Mock بودن همراه است.

## ۱۸. استقرار

هدف یک VPS ساده Linux با HTTPS است. روش پایه شامل Python virtual environment، سرویس systemd و Reverse Proxy است. Docker Compose فقط اگر در زمان استقرار واقعاً Setup را ساده‌تر کند افزوده می‌شود.

برای اجرای ۲۴/۷، Health Check، Restart Policy، Backup دیتابیس/رسانه‌ها، Log Rotation و راهنمای بازیابی لازم است.

## ۱۹. وابستگی‌های کارفرما

برای تست واقعی در زمان مربوطه نیاز است:

- OpenAI API Key با Billing و دسترسی مدل تصویر
- Telegram Bot Token و Channel ID/Username آزمایشی
- Bale Bot Token و Channel ID/Username آزمایشی
- Rubika Bot Token و Channel ID آزمایشی
- لوگوی PNG شفاف، فونت/رنگ برند و اطلاعات تماس
- حساب‌های تستی و افزودن Bot به‌عنوان Admin کانال با مجوز لازم
- در مرحله آخر، حساب WhatsApp آزمایشی و Pairing توسط مالک

تا قبل از آن، Mockها و ساختار کامل قابل پیاده‌سازی هستند.

## ۲۰. معیار پذیرش MVP

MVP پذیرفته است وقتی:

- مدیر محصول، عکس، قیمت، موضوع و Voice اختیاری را ثبت کند.
- عکس استودیویی OpenAI تولید شود، نسخه اصلی حفظ و خروجی قابل مقایسه باشد.
- لوگو/متن کوتاه دقیق روی عکس و کپشن کامل با ایموجی/هشتگ زیر آن ساخته شود.
- پیش‌نمایش عکس + کپشن + Voice در پنل وجود داشته باشد.
- Manual، Auto و Pause طبق Guardrailها عمل کنند.
- Telegram، سپس Bale و Rubika بر اساس شواهد واقعی یا وضعیت صریح Mock کار کنند.
- Voice در Telegram/Bale بومی و در Rubika حداقل به‌شکل فایل صوتی قابل‌پخش ارسال شود.
- شکست یک پلتفرم مانع بقیه نشود و Message ID/خطا ثبت شود.
- ربات خصوصی فقط به سؤالات مرتبط و Grounded پاسخ دهد و موارد نامعلوم را Escalate کند.
- Dashboard و نمودارهای کاربردی داده واقعی سامانه را نشان دهند.
- تست‌های اصلی Pass و README شامل Setup، Deployment، محدودیت‌ها و Credentials لازم باشد.
